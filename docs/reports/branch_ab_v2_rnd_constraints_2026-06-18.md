## Hard Constraints

1. WisecondorX-first remains mandatory.
   - `WisecondorX predict` and its CBS/segment evidence remain the primary CNV source.
   - Branch A is the high-sensitivity candidate discovery layer.
   - Branch B must not become a second standalone final caller.

2. Branch B V2 must be candidate-level.
   - Branch B V2 may compute genome-wide evidence tracks such as raw amplitude, corrected amplitude, flank contrast, sample noise, and region-risk burden.
   - Branch B V2 must only summarize and classify events from Branch A candidates.
   - B-only events must not enter the final report by default.

3. Every Branch A candidate must have an explicit final disposition.
   - Allowed disposition values:
     - `CONFIRMED`
     - `MOSAIC_SUSPECT`
     - `REVIEW_REQUIRED`
     - `LIKELY_ARTIFACT`
     - `NO_CALL`
   - No A candidate may disappear silently.

4. Missing evidence must stay unknown.
   - Missing refmap, mappability, blacklist, mask, or calibration-null evidence must be represented as `UNKNOWN` or `NaN`.
   - Missing evidence must not default to clean support, zero overlap, or zero low-refbin burden.

5. Hard filters must be narrow.
   - Hard filtering is allowed for QC failure, missing/corrupt files, or clearly unanalyzable regions.
   - Region-risk, weak Branch B signal, direction discordance, and empirical support gaps should usually produce downgrade/review reasons, not silent removal.

6. SCA needs a separate path.
   - Sex chromosome abnormality interpretation should become a separate Branch S shadow model.
   - Branch S must not initially replace current sex calling or final report logic.
   - Branch S should evaluate X non-PAR, Y non-PAR, PAR, sex-chromosome dosage, and SCA state scores.

7. All real validation must run on `ssh fengxian`.
   - Local work is limited to static code/document edits and repository review.
   - Remote executables remain:
     - Python: `/biosoftware/miniconda/envs/snakemake_env/bin/python`
     - Snakemake: `/biosoftware/miniconda/envs/snakemake_env/bin/snakemake`

### WisecondorX predict layer

The current Branch A source file is:

```text
wisecondorx/cnv/predict/{sample}_aberrations.bed
```

It is generated by `WisecondorX predict` with the workflow parameters from `rules/predict_layout.smk` and `predict_samples.yaml`:

| parameter | current default/source |
|---|---:|
| `convert_binsize` | `100000` |
| `zscore` | `5` |
| `alpha` | `0.001` |
| `maskrepeats` | `5` |
| `minrefbins` | `150` |
| `seed` | `1` |
| `preserve_branch_a` | `true` |
| `benchmark.branch_a_z_threshold` | `5.0` |

The predict rule runs:

```bash
WisecondorX predict <predict_npz> <reference_npz> <output_prefix> \
  --bed \
  --plot \
  --zscore <CNV_ZSCORE> \
  --alpha <CNV_ALPHA> \
  --maskrepeats <CNV_MASKREPEATS> \
  --minrefbins <CNV_MINREFBINS> \
  --seed <CNV_PREDICT_SEED> \
  [--blacklist <bed3>]
```

Therefore, Branch A sensitivity is primarily controlled by WisecondorX predict settings and reference/preprocess choice, not by downstream Branch A assembly code.

### Branch A assembly layer

`pgta/predict/branch_a.py` performs these operations:

1. Read the WisecondorX BED columns:
   - `chr` / `chrom`
   - `start`
   - `end`
   - `type` / `state`
   - `ratio`
   - `zscore`
2. Normalize chromosome labels to `chr*`.
3. Normalize event state:
   - `gain`, `dup`, `duplication` -> `gain`
   - `loss`, `del`, `deletion` -> `loss`
4. Drop malformed rows:
   - missing start/end/zscore/chrom/state,
   - non-positive intervals.
5. Merge only same-sample, same-chromosome, same-state intervals when adjacent or overlapping under `merge_gap_bp`.
   - Current workflow does not pass `--merge-gap-bp`, so the code default is `0`.
   - Opposite-state adjacent events are not merged.
6. For merged candidates:
   - length-weighted `a_ratio`,
   - maximum absolute source `a_zscore`,
   - `a_source_event_count`,
   - ranking by descending `a_abs_zscore`,
   - candidate IDs like `{sample}.A0001`.
7. Assign support level:
   - `strong` if `a_abs_zscore >= strong_z`;
   - `sensitive` otherwise.
   - Current workflow does not pass `--strong-z`, so the code default is `10.0`.

Tested behavior:

- Adjacent same-state WisecondorX calls are merged and ranked by absolute z.
- Opposite-state adjacent calls are not merged.

### What Branch A must not be changed into

The following are not current Branch A behavior and must not be introduced without an explicit RFC and remote ablation:

- adding artifact filters inside `pgta/predict/branch_a.py`;
- filtering by region-risk, blacklist, mappability, gap, centromere, telomere, or refmap at the Branch A assembly layer;
- using Branch B calibrated z, HMM state, mosaic fraction, clean fraction, or q-value to suppress Branch A candidates;
- raising WisecondorX predict `zscore` to reduce presumed-negative FP without proving no recall loss;
- changing `strong_z` semantics from support labeling into a candidate inclusion threshold;
- merging opposite-state events across the same chromosome.

### CNVpro borrowing validation scope

The older CNVpro/CNVseq workflows are method references, not replacement callers. The goal of this validation is to decide whether the following five evidence families should be promoted into the PGT-A Branch A/B workflow.

| borrowed method family | CNVpro source concept | Proposed PGT-A landing zone | Validation purpose |

## Branch A NPZ / Predict Rebuild Contract

When a new reference is built from additional reference samples:

1. Reference-sample NPZs
   - If FASTQ/BAM and binsize are unchanged, existing WisecondorX converted NPZs can be reused.
   - If mask/preprocessing strategy changes, mask-only NPZs must be regenerated.
   - If binsize changes, raw and mask-only NPZs must be regenerated for that binsize.

2. Predict-sample / Branch A NPZs
   - If binsize and preprocessing contract are unchanged, existing predict NPZs do not need to be regenerated.
   - WisecondorX predict must still be rerun against the new reference.
   - Branch A candidate files, Branch B evidence/classification, evaluation, benchmark, and report must be regenerated because reference residuals and candidate calls can change.

3. Branch B V2 evidence
   - Candidate evidence must be tied to:
     - reference ID,
     - binsize,
     - mask/preprocess version,
     - WisecondorX predict command,
     - Branch A candidate source file,
     - negative-bank version.
   - Evidence generated under different reference IDs must not be compared without recording the reference change.

4. Gender / SCA
   - Reference rebuild must not silently change sex calling behavior.
   - Branch S shadow output can compare sex-chromosome evidence but must not replace current sex call until separately validated.

### Phase 1B: maskpar/mapability asset decision matrix

Purpose:

- Do not repeat the prior generic overlap analysis unless a concrete gap is identified.
- Consolidate existing CNVseq unique-bin, repeat-mask, low-mappability, PAR, and maskpar evidence into a decision matrix for how these assets should enter the workflow.
- Decide between annotation-only, reference-build mask, and full remap/reference rebuild.

Existing evidence baseline:

- `docs/handoff/2026-06-11_2358_hg19_repeat_mask_probe_handoff.md` already evaluated CNVseq unique-bin and repeat-mask overlap against current kept events.
- That probe found the CNVseq AZF unique-bin complement did not directly explain the current chr6/9/11/16 false positives.
- It also showed repeat/segdup burden alone is unsafe as a hard event-level filter because true positives and false-positive-like events can share similar burden.

Decision matrix:

| option | Meaning | When to use | Required validation before promotion |
|---|---|---|---|
| `annotation_only` | Use `maskpar`, mappability, and unique-bin resources only as event/bin annotations. | Default first step, especially when prior overlap shows no clear FP-only separation. | Unit/static contract checks plus shadow evidence completeness. |

Current default decision:

- Do not replace the current `hg19.fa` alignment reference in production.
- Treat `hg19.mapability.fa.gz` and `maskpar` first as annotation/mask asset sources.
- `maskpar` is primarily a PAR/sex-homology interpretation aid; it should not become a global hard mask by default.
- If a future change moves from `annotation_only` to `reference_build_mask`, the new reference ID, binsize, mask version, and preprocessing contract must be recorded, and all downstream predictions must be rerun.
